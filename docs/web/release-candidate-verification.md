# Release-candidate verification (local combined tree)

Recorded 2026-10-02 by the webApp engineer session for task `TM-RELEASE-CANDIDATE-20261002-01`.

**What this is.** A **local, unpushed** branch, `codex/web-release-candidate`, that combines the reviewed web stack (PR #82 and everything under it) with native `main`, so that one tree can be built and tested end to end. It exists only to answer "does the combined tree compile, pass its tests and keep native's changes?"

**What this is not.** It is not a merge to `main` or to any shared branch, not a retarget, rebase or force-push of any source branch, not a deploy, and not a release. No provider, credential, resource, terms, rights, approval-flag or Start-policy change was made. **Local candidate acceptance below does not authorize any shared merge or public release;** those remain the owner's decisions.

### Failures observed, and what they were

1. **Environment, not code: first `:sharedLogic:jvmTest` run failed 16 of 349 tests.** The sixteen are the real-data audit tests (`ExerciseRouteRealDataTest`, `RouteGenerationRealDataAuditTest`, `VerifiedTrailAdditionsRealDataTest`). The message is `Unable to locate data/generated/mcgis-trails.normalized.json`: those inputs are gitignored private extracts, absent from any fresh worktree. They were copied (read only) from the native checkout into the candidate's ignored `data/generated/` (sha256 prefixes `310f1d50326a` mcgis, `23a9719dd452` mclean-access, `2f97e23b5d6d` verified additions), and the run in the table above passed all 349. Nothing in the repository changed. **Consequence:** a fresh clone or a hosted runner cannot run these 16 tests without the private extract; the same limitation applies to the copies of these tests under `shared/src/androidHostTest`; it is a data-access limitation, not a regression.
2. **No concrete combined-tree code failure was found.** No source file in the candidate differs from `main` or PR #82 except through the merge itself.

### Reproducibility observation (not a defect)

The candidate's core build output hash (`4f552090dbd3`) differs from the `63c6b5359fce` recorded for PR #82 in `ctm-web-parity`, though the core **inputs** hash is the same (`01bc47b1a4d7`). Comparing the two output directories, every `.mjs` file is byte-identical; only `TrailMapper-sharedLogic.mjs.map` differs, and its `mappings` and `sourcesContent` are equal. The parity checkout's map has `sources` paths pointing at the `ctm-web-44` checkout (the Gradle build cache had restored an artifact produced there), while the candidate's paths are relative to its own tree. So the output hash tracks source-map paths, not code. It is worth knowing when comparing hashes across worktrees; it changes nothing about the code.
