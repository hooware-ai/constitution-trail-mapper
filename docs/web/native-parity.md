# Native-to-web parity: matrix, evidence and implementation plan

Recorded 2026-10-01 on `codex/web-native-parity` (stacked on PR #81). **Direction from the owner (relayed by the architect): public web data, routing and map features must equal or exceed the current native phone feature set. The 254-feature county package is the review baseline, not launch scope. Launch stays guest-first** (no sign-in, route planning, foreground navigation, browser-local saves).

This document is a plan and an evidence record. It approves nothing: no data flag, no approval record, no rights conclusion and no release changes. Where rights are unresolved the matrix says so and the item is a **blocker with evidence**, never a silent reduction in coverage.

## Routing, safety and semantics

The web and native clients **share one routing core** (`sharedLogic`, built into the web as `webBridge`), so graph construction, snapping, edge weights, access penalty, closure gating and proposed opt-in are the same code. What differs is only what data the web hands it. The probe confirms, on identical inputs, that nothing in this list needs new routing logic:

| Behaviour                                                    | Evidence                                                                                                                                                                                                                                                                                 |
| ------------------------------------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Access roads are access legs only, never through-route edges | `routing-data-plan.md` ("not part of the approved trail route"); the bridge builds the access graph from the same `AccessGraphBuilderSijko` and reports access distance separately                                                                                                       |
| 600 m endpoint-local rule for OSM service roads              | Native `AndroidAccessNetworkJsonReader` keeps a feature of layer `osm-service` only if `AccessNetworkFeatureProximitySijko.isNearAnyPoint(..., 600.0)`; the **web bridge's `accessRoads()` applies the same function and radius per request**, and keeps every non-`osm-service` feature |
| Proposed trails are opt-in and preview-only                  | Probe, `+proposed` configuration: a loop that can use a Proposed segment does so only when `proposed` is requested, and the route is `blocked` (preview-only) in every case                                                                                                              |
| Unverified connections are never navigable                   | Probe: every route that includes an estimated access gap is `blocked`; none became navigable with more data                                                                                                                                                                              |
| No invented bridges                                          | The pond circuit (D3) and the Birky 26.7 m gap: the core never joins them (see targeted probe)                                                                                                                                                                                           |

**About the probe's use of the full access file.** `initialize` is given the whole access JSON because that is how the bridge receives it; the bridge then filters OSM service roads to 600 m per request exactly as native's reader does, and keeps all TIGER roads. So the probe's results reflect native's selection, but **holding the file in memory is not what native does** (native streams it per endpoint set). Experiments that include the whole file are labelled as such; the plan below makes the web load only what native would use.

## Demonstrated web-only defect that blocks access parity

`WebRoutingBridge.revalidate` (saved-route revalidation, added for #47) checks every trail edge of a route against geometry derived from a **trail-only** graph (`TrailGraphBuilderSijko.buildGraph(openNetwork.features)`). When the planner is given access roads, it builds a **combined** graph, and trail edges are split and anchored at nodes the access connectors introduce, so the drawn trail pieces are not in the trail-only reference set.

Measured with the real core on the native data (`parity-probe.mjs`): **27 of 27 freshly planned routes (15 point-to-point, 12 loops) are returned with `network.status: "stale"` and `geometry-changed` issues** (for example trails 16:3793 and 16:1441) and the warning "This saved route no longer matches the current trail data … Recalculate it before riding." Without access roads: 0 of 22. Because `canNavigate` requires `networkCurrent`, this blocks navigation by itself, independent of gaps, and it would also mark a reopened saved route stale. Native has no such check (the function exists only in `webBridge`), so native is unaffected.

This is a **web-only Kotlin source change** (`webBridge/src/commonMain/.../WebRoutingBridge.kt`, not shared or native code) and fixing it needs **one targeted Kotlin core rebuild** (`:webBridge:jsBrowserProductionLibraryDistribution`), run once, serially, in this worktree. The fix must derive the reference geometry the way the planner now builds it (trail graph plus the endpoint-local access graph the route used) while still rejecting a trail that moved or was redrawn; a regression must show a fresh access route verifies **and** that a changed trail still fails.

### Usable navigation: why the probe shows zero navigable routes

Two questions were folded into one number and are now kept apart (`node tools/navigation-equivalence.mjs`, real core, real assets):

1. **Does the core find a route?** Yes for every catalog pair and loop (27 of 27 in the delivery check above).
2. **May the rider start navigation on it?** Native: unless a blocking closure applies. Web: also not with an estimated access gap, a Proposed trail, or a stale network. Catalog places are street addresses, not trail vertices, so every catalog route begins or ends with an estimated (straight, unverified) access segment; native would show it dotted and allow Start, the web refuses by policy. That is the entire reason for zero navigable results; it is **not** evidence about native safety behavior and was previously misdescribed.

**Result (`node tools/navigation-equivalence.mjs`, real county and access assets; the same for the web data and the native data at default layers):**

| Sample                                                                                                                           | Core finds a route | Native could start | Web can start | Web refuses, reason                      |
| -------------------------------------------------------------------------------------------------------------------------------- | ------------------ | ------------------ | ------------- | ---------------------------------------- |
| 15 catalog place pairs                                                                                                           | 15                 | 15                 | **0**         | 15 x estimated access gap                |
| 12 seeded trail-vertex pairs (positive controls)                                                                                 | 9                  | 9                  | **3**         | 6 x estimated access gap (3 found none)  |
| Control A: endpoint 0.003 degrees north of a trail vertex (334 m from that vertex, measured 23 m from the nearest access road)   | yes                | yes                | no            | estimated access gap, 31 m in 2 segments |
| Control B: endpoint 0.0095 degrees north of a trail vertex (1058 m from that vertex, measured 12 m from the nearest access road) | yes                | yes                | no            | estimated access gap, 20 m in 2 segments |

So the web can and does start navigation on routes whose access is fully mapped (3 positive controls), and refuses every route that carries an unverified straight access segment, which is every catalog route. Closure blocking is common to both rules and is covered by the shared Kotlin tests and the web's recalculate flow; no catalog route crosses an active closure today, so it does not appear in this table. **Decision for the architect:** keep the stricter web rule (the standing "unverified connections are never navigable" policy) or align with native's rule for estimated access. Nothing here changes it.

The tool reports, per configuration, route availability, native-startable, web-startable, the web's blocking reasons, positive controls (trail vertex to trail vertex: startable on both rules where access is fully mapped), and negative controls. **What the negative controls are, precisely:** each is a point displaced due north of the first trail vertex by a chosen number of degrees (0.003 and 0.0095). The displacement is the chosen input; what it means for the network is measured and reported separately: 334 m and 1058 m from that vertex and from the nearest trail, but only 23 m and 12 m from the nearest access road, which is why the router draws short estimated gaps (31 m and 20 m). They are **not** points far from every road, and they are not evidence of behavior far from the network. They show one thing: a short unverified access gap is enough for the web to refuse Start where native would allow it. Closure behavior is covered separately, with real dates and the shared core's own closure rules, in `tests/unit/bridge-closures.test.ts` (before the Uptown closure begins, during it, and a year later with no automatic reopening; a route planned earlier is gated on inspect, a new search finds no route, recalculate gives the detour guidance, and the core refuses to open a ride on it) and in `tests/unit/bridge-reverse.test.ts` (a loop over the closure is blocked in both directions). A road-work notice (Hamilton/Rhodes) informs but never blocks, before and after its estimated end.

## Implementation plan and checkpoints

Everything below is synthetic or private-data-in-memory in automation; no real tiles, no network beyond loopback, no data flag or approval record changes.

1. **Provenance and rights seams (first).** Extend the dataset record so `omitted.supplements` and `omitted.accessRoads` become structured parts: each names its source, licence, attribution text and link, content SHA-256, byte size, feature counts and what it must not be used for (access legs only). The package tool gains **optional** inputs (OSM supplement and its manifest; access roads) that are verified against hashes and reviewed manifests, and a required `rights` block for any Proposed geometry (basis, evidence URL, evidence SHA-256); without that block the tool refuses to package Proposed geometry. The approval record, blockers and `approved: false` are untouched.
2. **Reviewed OSM ways.** Package the 4 ways as a separate supplement, verifying each way's geometry hash against the reviewed manifest before it is admitted; carry its ODbL attribution into the map credit and Help data section; keep the `excludedUntilVerified` gaps as gaps.
3. **Proposed opt-in.** Seam only: when a dataset contains no Proposed features the opt-in says so honestly instead of doing nothing. Geometry is added only through step 1's `rights` block, never invented.

6. **Map controls, closure-advisory gaps and device preparation**, after the data work, including the feature gaps above that need no provider.

### Lazy loading of the access asset: assessment

Measured on the native asset (read-only): it is pretty-printed, so the 15.3 MiB file is **about 6.5 MB minified** (TIGER 2.4 MB, OSM service 4.1 MB); the whole file is **about 1.25 MB gzipped and 0.8 MB brotli**. Splitting OSM service roads into 0.01° cells gives 439 non-empty cells (median 2 KB, 90th percentile 32 KB, largest 135 KB); a 3-by-3 window around an endpoint, which covers the 600 m radius, is at most about 0.9 MB raw and a fraction of that compressed.

Proposed design (no shared or native source change, no Kotlin rebuild):

- **Packaging** (separately provenanced, hash-verified): `access/base.<sha12>.json` (all TIGER roads, always needed once an endpoint is off-trail), `access/osm/<cell>.<sha12>.json` tiles holding **whole features** (a feature spanning cells is stored in each), and an `access/index.json` listing every file with its SHA-256 and size, itself hash-named from the dataset record. Minified and precompressed (gzip or brotli) by the packager; the dataset record states the compression and the per-part licence and attribution.
- **Loading.** Nothing is fetched at start-up or for a route whose endpoints are on the trail. Before an operation that needs access roads (plan, reroute, recalculate, revalidating a saved route that used them) the worker loads the base once and the tiles in the 3-by-3 window around each endpoint, verifies every file against the index hash, assembles the same JSON the bridge already accepts and re-initializes. The bridge's own 600 m filter then yields **exactly native's selection** (whole features, same function, same radius).
- **Failure.** A hash mismatch, a missing tile or no network is a visible, retryable error. The planner never silently falls back to a graph without access.
- **Memory.** The packaged base is parsed once; tiles are added and evicted by distance, so a phone never holds the 6.5 MB OSM layer.
- **Optional later optimisation:** an incremental `addAccess` operation in the bridge (a web-only Kotlin change that needs a core rebuild) would avoid re-initializing; it is **not** part of this plan because a core rebuild is out of scope.

### Regression tests that keep the 16 MB load off the phone

- **First load fetches no access bytes** (request log on a stubbed server): zero requests under `access/` before an off-trail plan; none for an on-trail route.
- **Bounded fetch**: an off-trail plan requests the base once and only the tiles in the window, and the total bytes stay under a stated budget; a second plan near the same place fetches nothing; a distant plan fetches only new tiles.
- **Equivalence**: for randomly chosen endpoints on a synthetic network, the lazily assembled access set equals native's filter (all TIGER-class features plus `osm-service` features within 600 m).
- **Integrity**: a flipped byte in a tile, a missing tile and an offline fetch each give a visible error with Retry and never a route that pretends to have access data.
- **Saved routes**: reopening a saved route that used access roads loads the needed tiles first and revalidates against them; it never reports `access-unavailable` merely because tiles were not yet fetched.
- **Size**: the artifact audit records the compressed size of each access part and fails if the initial (non-lazy) payload grows.

## Checkpoint 2: saved-route revalidation with access roads, and incremental access loading

- **Defect (web-only, now fixed):** with ordinary-road access loaded, 25 of 27 freshly planned routes were flagged stale. Core `webBridge` rebuilt serially. Probe: 0 of 27 fresh routes flagged stale in the access configurations (0 of 22 without access, as before).
- **Rule now:** trail-typed lines must still derive from the feature's own current geometry (a moved or redrawn trail is stale). Access-typed lines are checked leg by leg against the planner's access graph built for the route's own start and destination (same endpoint-local 600 m filter): every leg must lie along ONE reference segment of that graph (a road segment, an intersection connector the graph derived, or a node-anchored form of a run). There is no blanket distance tolerance: a hop between roads the graph does not connect, however short, has no reference and is stale (review P1 on 9088702; the first version's 8.5 m fallback accepted an invented bridge). A road that moved or vanished is stale. Core after this change: inputs `5d897882e1fd`, output `e7b5d2bca979`.
- **`addAccess` operation:** adds roads without re-initializing. Parsing has no side effects; duplicates inside a batch must be identical; an id already loaded must match in geometry, name, road class and endpoint-local status; any refusal changes nothing. Verdict and geometry caches are dropped when the loaded access data changes.
- **Tests:** `tests/unit/bridge-access.test.ts` (8, through the real core): composite-edge fresh route verifies; moved trail, redrawn vertex, moved road and removed road are stale; incremental load; idempotence, duplicate and metadata conflicts leave state unchanged; no endpoint-local leak from a refused batch; re-initialize owns its own access data; a legitimate short graph-derived hop verifies (control) and an invented out-and-back hop onto a parallel road is stale.

## Checkpoint 3: lazy hash-verified access delivery (architect corrections c, d, e)

**What ships (synthetic-tested, optional, off unless `--access-roads` is given to the packager):** the access roads are split so opening the planner downloads only the base roads, and a trip downloads only the service-road tiles around its endpoints.

- **Package** (`tools/lib/access-package.mjs`, `npm run package:dataset -- --access-roads <extract>`): `access-base.<sha12>.json` (every non-service road, loaded with the trails), `access-tile.<lat>_<lon>.<sha12>.json` (endpoint-local `osm-service` roads in 0.01° cells), `access-index.<sha12>.json` (every tile with size and SHA-256). Compact JSON, deterministic. The dataset record's `access` block pins the base and the index by hash; the index pins every tile. `record.access.combinedSha256 = sha256(network sha256 + ":" + index sha256)` is the identity a saved route remembers and the record `version` is named by it, so the same trails with different roads are a different dataset.
- **Whole-feature bbox assignment (correction e):** a road is written to every cell its bounding box intersects, never by centroid. The audit refuses a package where any road is missing from a cell its box touches, where a tile holds a road that does not touch it, and where tile content is not exactly what the index says.
- **Equivalence with native's 600 m rule:** native keeps a service road when any segment lies within 600 m of an endpoint. A 3 x 3 block of cells around the endpoint reaches at least one full cell (>= 845 m of longitude at this latitude, 1113 m of latitude) in every direction, and any road with a point inside that reach has a bounding box in one of those cells. The loader gives the core a superset; the core applies its own exact 600 m filter, unchanged. The design is refused above 56° latitude (the longitude cell shrinks; 56° is where 622 m still exceeds 600 m). Tests cover cell edges and corners, 599 m and 601 m, a nine-kilometre road whose centroid is far from the endpoint, and a road with no tile at all.
- **Every operation loads access (correction c):** no operation skips road loading because an endpoint looks like it is on a trail. `plan` (start, destination), `reroute` (rider position, route end), `recalculate` and the revalidating `inspect` / `snapshot` (the route's own first and last points, where the planner built its access) all load the tiles first. A map-tap preview does not use roads and does not load them.
- **Order matters, and is preserved:** the access graph merges nearby nodes in feature order. Real-data comparison found 3 of 27 plans differing by a few metres (a snapped node) when tiles arrived in a different order. Each service road therefore carries its position in the extract (`ord`), and the core presents late-arriving roads in extract order after every `addAccess`. Packaging refuses an extract that lists service roads before base roads.
- **Pinned identity and operation ownership (correction d):** the worker verifies the combined identity, fetches only files the pinned record names (hash-named, immutable), and handles messages strictly in arrival order, so a boot never overtakes an operation still loading its roads and a failed operation never poisons the next. A cancelled or crashed worker is replaced by one that boots from the pinned record and loads tiles on demand; a restored ride's first revalidation loads the roads around its own endpoints before the check (without that, the same route is not verified). Each operation's load and dispatch are one step, so another operation's `addAccess` cannot land between them.
- **Failures are visible and retryable:** a download failure ("could not be downloaded; check your connection and retry"), a missing file, a hash or size mismatch ("failed its integrity check, so it was not used") and an index that disagrees with its record are reported with their error code. A failed tile is never counted as loaded, and the next attempt on the same session succeeds.
- **Rider-facing:** Help's data section lists the road access (counts, sources, ODbL link) and the map credit names OpenStreetMap when service roads are present; where no road connects a point to a trail the access stays a labeled gap, never an invented connection.

**Evidence (real native assets, in memory only; nothing committed or served):**

- Size (`node tools/analyze-access.mjs`): the 15.7 MB access extract becomes base roads 1.9 MB raw / 624 KB gzip / 378 KB brotli (3,424 roads), a 78 KB index (23 KB gzip), and 440 tiles totalling 2.2 MB raw / 510 KB gzip, from 9,313 service roads (10,323 tile assignments, so whole-feature duplication is about 11%). A trip downloads the index plus 11 to 17 tiles: 6 to 50 KB gzip.

Each of the 27 routes was then re-checked as a cold restored ride (a brand-new core instance and loader, base roads only, the session loads what the route needs) with a verdict identical to the reference.

## Checkpoint 6: ridden progress, ride ownership and the map cues

**Ridden progress is not complete native equivalence.** What the web keeps is native's rule for how far the rider has credibly ridden (the shared `TrailRouteRiddenProgressSijko`: on-route fixes only, forward steps up to 300 m, a larger jump held until 150 m of continued travel confirms it), plus the saved value across a reload. Three honest limits:

- **Legacy fallback (rides saved before ridden progress was stored):** restored as the lesser of the matched progress and the observed distance. This is **intentionally conservative and can undercount** (for example after a long observed ride that was matched further along than it was ridden); it never overcounts, and a rejoin from it errs toward riding more of the loop. It is a fallback, not the native value.
- **A pending jump is not persisted.** Native keeps its pending jump across a restart; the web keeps only the ridden value. After a reload a jump that was waiting for confirmation has to be re-established by continued travel, which can only delay crediting, never credit too much. Covered by a test: a reload that lands more than a kilometre ahead on the loop moves where the rider is matched but not what was ridden, is not carried by a rejoin, survives a second reload unchanged, and is credited only after 150 m of confirming travel (the control).
- **Observed distance across a rejoin** carries over from the same ride; per-route ridden progress starts again on the replacement route, as in native.

**Ride ownership.** A finished loop ends its own ride synchronously and only records its history afterwards; a rejoin finishes every await before the ownership check and adopts in one synchronous step; reversals are gated on a fresh navigable verdict and drop the ride (and its credit) when blocked. Each has a hold-and-release regression that changes the worker's answer for one operation and releases it after the ride has moved on.

**Map cues.** `mapCues` returns direction-ordered pieces (a second pass already shifted 8 m to the right), turn-arounds with their distance along the route, and the navigation distance at every point. The web draws the pieces, chevrons every 110 px (the placement native's share image uses), the Turn around sign, and the faded ridden overlay from them.
