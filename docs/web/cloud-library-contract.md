# Saved-library foundation: contract, rules and local emulator (issue #31, local slice)

This is the **local foundation** for private saved routes and places: a versioned record contract, TypeScript validators, synthetic fixtures, default-deny Firestore rules and emulator security tests, payload measurements, and the ownership rules a later sign-in/sync adapter must follow. It runs only against the **local Firestore emulator** under a `demo-` project id. Nothing here is deployed, nothing talks to a real Firebase project, and there is no sign-in, no sync and no UI wiring in this build (#32/#33 are separate, later work).

## What is saved, and what never is

Only things a rider **intentionally saves** become cloud records: **routes** and **places**. These are never uploaded as a side effect of signing in: recents, planner drafts, search text, the active ride, completed-ride history, live GPS. The county trail graph or any dataset content is never uploaded either: a route record carries the dataset's **identity** (kind, id, version, SHA-256), not its data. Saved routes and places do contain the locations the rider chose; the Help dialog says so.

Collections, one Firebase UID namespace per environment:

    users/{uid}/routes/{routeId}      schema trail-mapper.saved-route, version 1
    users/{uid}/places/{placeId}      schema trail-mapper.saved-place, version 1

## The record contract (version 1)

Source of truth: `webApp/src/cloud/contract.ts`. It exists in two forms: the **document** form stored in Firestore (native timestamps, `engine` as bytes) and the **interchange** form (JSON: RFC 3339 timestamps, `engine` as base64) used by fixtures, other platforms and the validators.

Route fields: `schema`, `version`, `id` (stable, client-generated, 16-64 of `A-Za-z0-9_-`, never reused for another record and unchanged by recalculation), `ownerUid` (immutable, equals the path uid), `routeKey` (`route-<16 hex>`: hash of the route's own geometry, the local library's key; changes when the route is replaced), `title`, `kind` (`Navigation` | `ExerciseLoop`), `draft` (planner choice: `mode` point/loop, `start`, `destination` or null, `miles` or null, `proposed` opt-in), `lengthMeters`, `bounds` (south/north/west/east), `geometry`, `pointCount`, `dataset` (`kind` fixture|county, `id`, `version`, `contentSha256`), `createdAt`, `updatedAt`, `revision`, and optional `engineCodec` + `engine`. Place fields: `schema`, `version`, `id`, `ownerUid`, `label`, optional `address`, `latitude`, `longitude`, `createdAt`, `updatedAt`, `revision`. Unknown fields are refused, in the validators and in the rules. A `Navigation` route must have a point-to-point plan and an `ExerciseLoop` a loop plan (validators, builder and rules agree).

- **Coordinates** are WGS84 degrees. Named fields are `latitude`/`longitude`. In the polyline, **latitude comes first**.
- **Geometry** is the display line: one path per drawable segment, `T:`/`A:` (Trail/Access) followed by an encoded polyline, lower case (`t:`/`a:`) when the segment is estimated rather than routed, joined by `;`. The polyline is the familiar encoded-polyline family at **1e-7 degree (about 1 cm)** precision, deltas zig-zagged into 5-bit groups, with no bitwise arithmetic so it is portable. Test vector: the three points (40.5, -88.99), (40.5, -88.97), (40.52, -88.97), in that order, encode to the following (a backtick is part of the text):

      _sfncW~|dj`t@?_seK_seK?

- **Engine payload** (optional): the routing engine's own serialized route, UTF-8 JSON, gzip-compressed (`engineCodec: "gzip-json/1"`). Its structure is validated when it is read (an object with a known `kind`, a positive length, and segments whose points are finite in-range numbers), its kind and length must agree with the record, and its geometry must equal the declared geometry; the builder runs the same shape check on the route before it reads or encodes anything, and re-checks its own output with the reader, so a malformed route fails with a `CloudRecordError` before any write; a payload that is missing a coordinate, has a non-numeric one, or contradicts the record is refused with a `CloudRecordError`. The compressed bytes are made platform-independent (the gzip header OS byte is fixed) and fixtures are compared by meaning, not by compressed bytes. It is what the engine needs to **revalidate** the route against the dataset loaded now (per-edge feature identity, status and geometry). A reader without the engine payload, or that cannot use it, treats the route as **needing recalculation from `draft`**; it never navigates from display geometry alone. A decompressed payload is capped (12 MiB) so a small compressed value cannot expand without bound.
- **Dataset provenance and revalidation identity**: `dataset` says what the route was planned on. Opening a saved route always re-checks it against the dataset loaded now (the existing current-network revalidation, PR #75). Only `fixture` and `county` data may be saved; **private local-review data never uploads**, and fixture records stay distinguishable from county records by `dataset.kind`, so a county build never opens a fixture record as if it were real and the reverse. Whether production rules should refuse `fixture` is a deployment decision; today both are accepted so the emulator can exercise fixtures.
- **Timestamps** in the interchange form must be real RFC 3339 instants (date, time and zone offset all present, a valid calendar day) and `updatedAt` may not precede `createdAt` (compared as instants at full nanosecond precision and across zone offsets; leap seconds are not accepted); anything else (`"2026"`, `"1"`, a 13th month) is refused. In a Firestore document they are assigned by the server (`createdAt == updatedAt == request.time` on create; `updatedAt == request.time` and unchanged `createdAt` on update): a client cannot choose them.
- **Versions**: `version` is an integer; this build supports `[1]`. Any other value is refused whole (`unsupported-version`), never partly understood. A future version change must update `SUPPORTED_VERSIONS`, the rules and this document together.

### Conflict and deletion semantics

- **Optimistic concurrency by revision.** A create is revision 1. An update must write exactly `revision + 1` of the stored record. Two devices that both read revision N and both write N+1: the first wins, the second is refused by the rules and must re-read and merge; nothing is overwritten silently. A stale or skipped revision is refused.
- **Identity cannot be reassigned.** `id`, `ownerUid`, `schema`, `version` and `createdAt` are fixed once written.
- **Replacing a route** (recalculation) is an update to the **same record**: same `id`, same owner, same `createdAt`, new geometry/`routeKey`/engine, `revision + 1`. The local library's key changes with the geometry, which is why `routeKey` is separate from the record `id`.
- **Deletion is a hard delete.** The record is gone (privacy and account deletion need that); there is no tombstone. An edit of a deleted record is refused (the update finds nothing). A recreate with the same id would be a new revision-1 record: adapters must not replay a queued create for an id the rider deleted elsewhere, and treat a failed update of a vanished record as "deleted elsewhere", preserving the rider's unsent edit for their decision. This is a documented limit, not something the rules can fully prevent.
- A **partial or invalid save never happens**: a record is one document, written atomically, and a route that cannot fit fails in the builder before anything is sent.

## Measured sizes and the supported representation

A Firestore document is capped at 1 MiB, and the engine's full serialized route is too large to store as is: an 8.5 mile real route is 485 KB of JSON and a 24 mile loop is **1.12 MB**. The saved representation stores the display geometry as a polyline plus the engine route **gzip-compressed**. Measured with `npx tsx tools/measure-cloud-payload.ts` on the real county package (real geometry, planned by the real core):

| Route                         | Local route JSON | Engine payload (gzip) | Geometry chars / points | Approx. document |
| ----------------------------- | ---------------- | --------------------- | ----------------------- | ---------------- |
| point-to-point 8.5 mi         | 485 KB           | 67 KB                 | 5,356 / 1,174           | 75 KB            |
| 5 mi loop                     | 185 KB           | 22 KB                 | 2,095 / 392             | 27 KB            |
| 10 mi loop                    | 387 KB           | 51 KB                 | 4,057 / 861             | 58 KB            |
| 25 mi loop (23.9)             | 1.12 MB          | 147 KB                | 12,042 / 2,666          | 161 KB           |
| 50 mi loop                    | 1.51 MB          | 187 KB                | 15,141 / 3,137          | 205 KB           |
| 100 mi loop (planner maximum) | 2.22 MB          | 260 KB                | 20,916 / 4,134          | 283 KB           |

Limits (`LIMITS`; identical in the rules): geometry 240,000 characters and 40,000 points, engine payload 640,000 bytes, route length 400 km, titles/labels 120 characters, addresses 200. Together the two big fields stay near 880 KB, under the 1 MiB cap, with about **2.3x headroom over the longest route the planner can make** (and the 100-mile loop is the planner's own maximum). A route that exceeds a limit **fails in the builder with `payload-too-large` before anything is written**; the rules refuse the same payload independently. The large fields are exempted from indexing in `cloud/firestore.indexes.json` (Firestore indexes would otherwise reject values above 1,500 bytes), and no query needs them.

## Firestore rules

`webApp/cloud/firestore.rules` is **default deny**. A signed-in user can reach only `users/{their uid}/routes/**` and `.../places/**`. Every record write must satisfy the full contract: allowed keys only (`hasOnly`/`hasAll`), schema, supported version, `id` equal to the document id, `ownerUid` equal to both the path uid and `request.auth.uid`, text lengths and single-line text, coordinate bounds, planner mode consistency, bounding box sanity (and the rider's own start/destination inside it), dataset kind and digest format, size and point-count bounds, engine codec, server timestamps and revision. Lists must carry a `limit` of at most 200; a collection-group query matches no rule and is denied. Everything else, including `users/{uid}` itself, is denied.

**What a rule cannot do**, so the validators do: a rule cannot loop, so it cannot check each coordinate of the geometry, decode a polyline, or compare `pointCount` with what is encoded. It bounds size, count and the declared box; every client validates point by point with `parseRouteRecord` before writing and when reading. `tests/support/cloud-mutations.ts` is the single table of 60+ ways a record can be wrong, with what the validators and what the rules must each do; rows where they differ carry a note explaining the limit, and `tests/unit/cloud-rules-agreement.test.ts` fails if any number in the rules and in the contract differ.

## Running the emulator tests (no credentials)

Prerequisites: Node 22.12+, **JDK 21+** (set `JAVA_HOME`; the runner checks it and puts it first on `PATH`), network access the **first** time only, to fetch `firebase-tools@15.32.1` through `npx` and the Firestore emulator jar (about 60 MB, cached in `~/.cache/firebase/emulators`). No Firebase login, project, key or service account is used, and the `demo-` project id means the emulator cannot reach a real project.

    cd webApp
    npm run test:rules                 # or: node tools/run-emulator-tests.mjs [tests/rules/<file>.test.ts]

On Windows the runner works with the inherited `Path` spelling (it never creates a second `PATH`), and on POSIX it passes paths with spaces as plain arguments without quotes; `tests/unit/emulator-invocation.test.ts` covers both. The runner picks a free loopback port it owns (it never reuses a running emulator), writes a throwaway config, starts the Firestore emulator only, runs `tests/rules/*.test.ts`, and stops it. `cloud/firebase.emulator.json` is a sample config (port 18080, UI disabled) for starting an emulator by hand: `npx firebase-tools@15.32.1 emulators:start --only firestore --project demo-trail-mapper --config cloud/firebase.emulator.json`. `firebase.json`, `.firebaserc` and every local credential file stay ignored by Git. The unit tests (`npm test`) do not need the emulator or Java.

### Hosted check: "Web Firestore rules"

`.github/workflows/web-firestore-rules.yml` runs the emulator tests on GitHub-hosted Linux so a change to the rules, the contract or the tests cannot merge unnoticed. It is a **separate workflow from `Web release check`**, which is unchanged.

- **Exact check name on a pull request:** `Web Firestore rules / Firestore rules emulator tests` (workflow `Web Firestore rules`, job `rules-emulator`).
- **When it runs:** `pull_request`, pushes to `main` and `codex/web-app`, and manual `workflow_dispatch`, when something under `webApp/cloud/`, `webApp/src/cloud/`, `webApp/tests/rules/`, the cloud test support/fixtures/unit tests, the emulator runner and invocation tooling, the negative-control tooling, `webApp/package.json`/`package-lock.json` or the workflow itself changes.
- **Steps (ubuntu-24.04, JDK 21 Temurin, Node 24, `contents: read`, no secrets, 30 minute job limit):** locked `npm ci`; unit tests for the contract and the gate's own tooling (no emulator); `npm run test:rules:prefetch` (fetches the pinned `firebase-tools@15.32.1` and the Firestore emulator jar on the clean runner, 10 minute limit, so a download failure has its own clear error and nothing depends on a developer's cache); `npm run test:rules` (all 75 owner / signed-out / cross-account / validation tests; any failing test, a crashed emulator, a timeout or a missing JDK exits non-zero and fails the job); `npm run test:rules:controls -- --skip-baseline` (negative controls); then an unconditional sweep for a stray emulator process.
- **What it verifies:** the committed `cloud/firestore.rules` against the **local** emulator under `demo-trail-mapper` -- default deny, signed-out refusal, owner-only access, A/B cross-account isolation, owner spoofing, record-shape/version/coordinate/size validation, revision conflicts, server timestamps and bounded lists -- and that these tests really can fail (see below).
- **What it does not verify:** that production is configured (no real project, database, provider, OAuth client, authorized origin or deployment exists or is touched), sign-in, sync, App Check, the web UI wiring, the native apps, or the data rights for any dataset. Real-environment configuration stays **UNVERIFIED** (see [hosting-runbook.md](hosting-runbook.md)).
- **No credentials:** the workflow holds no secrets and never authenticates. The runner also removes `GOOGLE_*`/`GCLOUD_*`/`FIREBASE_*` credential and project variables from the emulator's environment (`withoutCredentials`, covered by `tests/unit/emulator-invocation.test.ts`), so even a runner that had them could not reach a project.
- **Bounded time and cleanup:** the runner enforces `TRAIL_EMULATOR_TIMEOUT_MS` (stops the emulator, SIGKILL after 10 s, exits 124), forwards `SIGINT`/`SIGTERM`, and uses a port it owns with no reuse of any running emulator; `firebase emulators:exec` stops the emulator it started when the tests finish.
- **Logs:** everything the run prints is also written to `$RUNNER_TEMP/rules-logs`, and on failure that directory is uploaded as `firestore-rules-logs` (7 days). It holds only synthetic fixture data and demo-project output.
- **Negative controls (`npm run test:rules:controls`, `tools/rules-negative-control.mjs`, patterns in `tools/lib/rules-controls.mjs`):** each control writes a weakened or malformed **throwaway copy** of the rules to the OS temp directory (the committed file is never modified and the copies are deleted), points the same runner at it with `TRAIL_RULES_FILE`, and requires the suite to fail for the right reason. Controls: default-allow, signed-out allowed, any signed-in user, no field validation, owner spoofing, no revision check, client-chosen timestamps, unbounded lists, no size bounds, and a malformed file (the emulator refuses to compile it). Without `--skip-baseline` it first proves the unmodified rules pass. `tests/unit/rules-controls.test.ts` fails if a control stops matching the rules after an edit, so a control can never silently weaken nothing. To reproduce locally: `cd webApp && npm run test:rules:controls` (about 3 minutes; `-- --only <name>` runs one).
- **Branch protection and admin setup remain unconfigured.** This change adds the check only; making it a required status check, or any repository/organization setting, needs a separate explicit authorization.

First hosted/local runs download the emulator (about 60 MB) from Google through the pinned tooling; subsequent local runs reuse `~/.cache/firebase/emulators`. Caching in CI is intentionally not used, so every hosted run proves the clean-machine path.

Dependencies added (dev only, nothing ships to riders): `firebase` 12.19.0 and `@firebase/rules-unit-testing` 5.0.2. `npm audit` reports 5 high advisories, all in the dev dependency tree (`@grpc/grpc-js` <= 1.13.5 pulled in by those test packages); `npm audit --omit=dev` reports none, and the tests only talk to a loopback emulator. They are not fixed here because the only offered fix is a forced downgrade of the test tooling.

## Account-aware observation, stale results and pending writes (contract for later adapters)

Specified as small pure code with tests, `webApp/src/cloud/ownership.ts`, and **not wired into the app**. The failure it prevents is a read, listener or queued write started for account A being delivered after the rider switched to B or signed out, and A's records or outcomes appearing in B's library.

- Every account change (sign-in, sign-out, switch, deletion) moves a single **epoch**. Capture an `ObservationToken` (epoch + uid) **before** starting any read, listener or write and present it with the result.
- `acceptDelivery` shows a result only if the epoch is unchanged, the token is for a real account (never signed-out), the data was read for that same uid, and then **only the records whose `ownerUid` is that account**. Anything else is dropped, including after switching back to the same account (it is a new session).
- **Pending writes belong to the account that made them** (`PendingWrites`). They are invisible to and never sent for any other account, survive ordinary sign-out (a sign-out never deletes cloud saves or loses an unsent save), settle only the originating account's ledger when a late callback arrives, and say whether that account is the one on screen. A **conflict** or **rejection** stays for the rider to resolve; a **commit** or **deleted elsewhere** ends the write. Deleting an account discards its pending writes and nobody else's.
- Observation is always **bounded**: the rules refuse a list with no limit or one above 200, so adapters page.
- Adapters keep the Firebase SDK behind platform interfaces; the contract above is serialized records, not SDK objects.

Also specified here for #32/#33/#35/#36 (nothing implemented): **linking** an additional provider happens from an authenticated account, requires re-authenticating the new provider and any consent for Apple's anonymized data, and preserves the existing UID, records and pending-write ownership; if the credential already belongs to another Firebase account, both libraries are preserved and the conflict is recoverable, with **no automatic merge** and **never matching on email** (Apple Hide My Email may supply a relay address). **Account deletion** requires re-authentication, revokes the provider where applicable (Apple), deletes the account's cloud records, local caches and pending writes; ordinary sign-out deletes none of the cloud saves.

## Interoperability fixtures

`webApp/tests/fixtures/cloud/` (generated by `npx tsx tools/generate-cloud-fixtures.ts`; a test fails if they drift): valid point-to-point, loop, no-engine and place records, and `invalid-records.json` where each invalid record names the error code a conforming reader must report and none may open partly. They are **synthetic**: self-authored geometry, fixture dataset provenance, no real place, rider or county data, so Android/iOS adapter checks (#35/#36) can reuse them. The web <-> Kotlin proof is `cloud-roundtrip.test.ts`: a route planned by the shared Kotlin core is saved, read back, handed to the core again, and inspects as the same route (identity, edges, geometry within 1 cm), including after a replacement. No native or `sharedLogic` source was changed.
